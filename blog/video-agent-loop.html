Video Agent Loop：StarCut 的双循环架构，DeepSeek Harness 能接住吗？

2026-08-18 · 更新于 2026-08-21

假设用户让 Agent 做一条三十秒的新品视频。Agent 看过当前项目，决定先生成一组产品特写；任务刚发出去，这一次模型运行就结束了。

素材还在生成，创作者没有停下来。他可能已经把开场从三秒剪到一秒半，删掉原来的镜头，又补了一句旁白。等图片返回时，Agent 面对的已经不是刚才那个项目。

这才是视频 Agent 的核心问题：一次模型运行很短，创作现场却持续变化。系统不只要记住“发出了什么”，还要让结果回来以后重新进入判断，而不是机械执行一份过期计划。

先把结论放在前面：StarCut 最终也没有离开这条基本循环，只是把它分成了两个时间尺度。内层是一次 Run 里的多 Step ToolLoop；外层是跨 Run、跨进程的持久 Session 恢复循环。下面从最小的一圈开始，看它为什么会一层层长成现在的样子。

一、先把 Agent 还原成一个 ToolLoop

大家经常用 ReAct 描述 Agent：reasoning、acting，再 reasoning。这个概念没有错，但它太容易停留在模型“会思考、会行动”的抽象层。工程真正需要实现的，其实只有一条可以运行的链路：

模型接收上下文，决定直接回答，或者输出一个结构化 Tool Call。Harness 校验参数、执行工具，把 Tool Result 放回上下文；模型拿到新的事实以后，再发起下一次请求。直到模型结束这次工作，或者触发停止条件。

我们更愿意把它叫作 ToolLoop。因为这个名字直接说明了系统必须做什么，没有暗示模型内部存在一套不可见的工作流。

这里先分清三个尺度：

  • Step：一次模型请求。它可能输出文字，也可能调用一个或多个工具。
  • Run：一个进程中连续发生的多个 Step。模型调用工具、读取结果并继续，通常都在这一次 Run 里完成。
  • Session / Thread：用户看到的一项持续任务。它可以跨越多次 Run，甚至跨越进程重启和浏览器断线。

StarCut 的内层循环选择了 Vercel AI SDK 7 的 ToolLoopAgent。原因很直接：模型适配、Tool Calling、Schema 校验、多 Step、流式输出和停止条件已经是通用问题，没有必要为视频业务重新实现一遍。我们真正要设计的，是这个通用 Loop 之外的运行边界。

二、Tool 是手，Skill 是说明书

模型本身既看不见项目，也改不了时间线。它能做什么，取决于系统给了它什么样的手和感知系统。

Tool 是一个可执行接口。它有名字、输入 Schema 和结果。模型调用 read，真的读取当前项目；调用 edit，真的修改时间线；调用 run_task，真的提交一次生成任务。

Skill 不执行任何事情。它是按需加载的领域方法：怎样组织一条时间线，什么时候需要安全区，图片生成该选择哪类输入，MG 动画有哪些可编辑属性。Skill 教模型怎样组合 Tool，却不能替 Tool 完成工作。

这一区分很重要。把所有方法都塞进系统提示词，上下文会越来越重；把每个工作流都固化成一个大 Tool，能力又会越来越僵。StarCut 只把 Skill 的名称和用途放进基础上下文，需要时再加载全文；Tool 则保持稳定、可校验、可执行。

一个视频 Agent 的基础工具大致分为四组：

能力代表 ToolAgent 得到什么
感知glob、grep、read、head、query项目结构、当前内容、素材信息和可用模型
操作write、edit、client_call修改工程、播放预览、渲染或抽帧
协作ask_user从用户取得只有用户能决定的信息
异步run_task、clock提交长任务，或者在未来重新唤醒 Session

到这里，一个普通 ToolLoop 已经能工作：查询模型、读取项目、编辑时间线、取得结果，然后继续。但视频创作很快会把这个循环撑破。

三、视频创作为什么把一个 Loop 撑成了两层

第一个问题是执行位置不同。模型目录和素材目录的查询适合在服务端执行；时间线、播放和本地渲染只能在真实 Editor 中执行；生成图片和视频要交给后台 Worker；创作取舍则要等用户。

第二个问题是时间尺度不同。一次查询只要几毫秒，一次编辑可能几百毫秒，一张图片需要数秒，一段视频可能需要几分钟。让模型进程一直等着，不但浪费资源，还会把系统正确性绑在网络连接和容器寿命上。

第三个问题是Session 比 Run 活得久。用户关掉网页、Worker 重启、部署替换容器，都不应该让已经提交的工作和刚才的对话消失。

这三个约束共同推出 StarCut 的双循环：

内循环推进当前判断，外循环把变化后的世界重新交给 Agent。

内循环是一次有限 Run。它先从数据库恢复对话历史，领取 Inbox 中的新输入，再组装当前项目、记忆和按需 Skill，启动一个 ToolLoopAgent。Run 中可以连续完成多个 Step；如果用户在中途补充信息，新的消息会在下一个 Step 边界并入上下文。

这一次 Run 有两种输出。模型文字和 Tool 参数以 Delta 持续流向界面，让用户立即看到进度；完整消息和完整 Tool Call 则写入持久历史。前者负责体验，可以断；后者负责恢复，不能丢。Run 只有在完整消息保存以后，才确认本批 Inbox 已经被消费并释放运行租约。

外循环不是另一个永远运行的模型循环。它是一个消息驱动的恢复机制：用户回答、Tool Result、Monitor 上下文和 Clock 提醒先进入 Inbox；如果当前 Run 还活着，它会在安全边界读取；如果当前 Run 已经结束，系统重新取得 Session 租约，从持久历史启动一个新的 Run。

这也是 DeepSeek Harness 真正值得观察的地方。它的 append-only Session Log、Inbox 和可替换 Agent Loop，覆盖的正是这层通用问题。但视频项目、后台 Task 和浏览器执行权是否能在不复制状态的前提下接进去，要继续往下看。

四、一条 Tool Call，怎样跨过四种执行边界

模型只应该知道“我要调用什么能力”，不应该知道当前是哪台服务器、哪个浏览器标签页或哪一个 Worker 在执行。于是我们把 Tool Call 本身和执行位置拆开。

完整 Tool Call 先被保存为一条已提交消息。消息流让 UI 和各类执行组件都能看到它，但看见不等于有权执行。系统根据 Tool 的执行策略选择处理方式：

  • ask_user 的执行者是人。
  • query、load_skill、clock 和 Task 提交由 Server Runner 处理。
  • read、write、edit 和 client_call 交给一个明确指定的 Client Runner。
  • 图片、视频、语音和转写最终由独立 Task Worker 完成。

它们有不同的执行者，却共用同一个结果协议：普通结果携带 toolCallId 进入 Inbox，找到原来的 Tool Call。当前 Run 正在等待，就直接进入下一个 Step；Run 已经结束，就在下一次恢复时把原调用补成“结果可用”。

ask_user：最纯粹的跨 Run 恢复

ask_user 故意没有 execute。模型发出问题后，系统保存开放中的 Tool Call，当前 Run 就可以结束。Editor 从已提交消息中渲染问题；用户回答以后，答案作为这个 Tool Call 唯一的 Result 进入 Inbox，并启动新的 Run。

这条链路验证的不是 Client Runner，而是更基础的一件事：旧进程已经不存在，Session 仍然能沿着同一个 Tool Call 继续。

query：为什么需要 Server Runner

生成图片之前，Agent 先用 query 按用途查询可用模型；做配音时，也先查询模型支持的声音。这个查询发生在服务端，但我们没有把它直接写进通用 Loop。

Run 先保存 Tool Call，Server Runner 订阅已提交消息，调用服务端的查询能力取得权威目录结果，再用 toolCallId 写回 Inbox。通常结果很快，正在等待的 ToolLoopAgent 会在同一次 Run 中继续。

多走这一圈的价值不是“异步”。它建立了一条一致边界：通用 Loop 只管理 Tool Call 生命周期，应用层决定 Tool 的真实实现；即使进程在调用保存后崩溃，开放中的调用仍然可以重新发现。

五、外部 Agent 怎样进入同一块画布

视频编辑器不能被简化成一组服务端数据。Agent 要面对的是用户此刻正在创作的项目：既要修改内容，也要播放、预览、抽帧和渲染。

我们选择浏览器，不是因为浏览器更容易实现这些能力。恰恰相反，Native 应用更容易持有本地运行时。但浏览器获客更直接，链接更容易传播，也能被 Codex、Claude Code 等外部 Agent 打开并进入同一个编辑现场。这是产品约束，由此才推出 Client Runner 和长期连接，而不是先有技术方案再找理由。

无论是 StarCut 内置 Agent，还是外部的 Codex，它们都不应该通过屏幕坐标和鼠标动作控制画布。它们操作的是视频项目的语义：读取已有结构、插入素材、调整顺序、修改属性，然后要求 Editor 播放或预览。画布是操作结果，不是 Agent 接口。

内置 Agent 从自己的 ToolLoop 进入；Codex 等外部 Agent 则通过 MCP 打开项目、调用 StarCut 的语义能力。StarCut 不需要合并两边的 Session：每个 Agent 保留自己的推理过程，只在项目能力这一层相遇。

如果以后提供 CLI，它只是另一种入口：更适合终端、脚本和自动化，但不应该在命令行背后再实现一套视频编辑器。这也暴露了下一步要升级的方向：把真正的产品边界从 MCP 提升为统一的 Project API。MCP、CLI 和内置 Agent 都只是适配器；一种能力只定义一次，入口可以增加，项目语义不能分叉。

API 化也不等于把所有东西都搬到服务端。项目读取和结构化编辑可以直接走统一通道；播放、预览、本地渲染这类必须依赖现场的能力，仍然交给在线 Editor。平台决定调用去哪里，调用者不需要知道背后是哪一个进程完成的。

能看见调用，不等于拥有执行权

这也是浏览器仍然需要长连接的原因：系统要知道哪个 Editor 在线、具备什么能力，以及多窗口同时打开时谁代表当前编辑现场。三个窗口都可以看到调用，但只能有一个接受执行，否则一次“插入片段”会在画布上发生三遍。长连接解决的是现场发现和执行权交接，不是再造一套编辑协议。

六、媒体长任务：为什么 Result 之后还需要 Monitor

Agent 查询到合适模型以后，调用 run_task 生成图片、视频或语音。但提交长任务以前，系统必须先记住它属于哪次调用、结果应该回到哪里；否则 Task 虽然完成了，Agent 却再也找不到它。

图片、视频、语音、MG 和 SVG 生成当前不阻塞 Run，提交后立即得到 monitoring；转写允许有限等待，三十秒内完成就直接返回，超过时间再转入监控。快结果留在当前 ToolLoop，慢结果则脱离模型进程继续。

这里有一个容易被忽略的协议约束：一个 Tool Call 只能有一个 Result。如果 run_task 已经返回“任务已进入监控”，几分钟后的成片不能再成为它的第二个 Result。

Monitor 观察变化，但不把通知当成事实

后台任务完成以后，先保存自己的最终状态，再发出一条变化信号。Monitor 收到信号后重新读取任务；信号可以重复、迟到，甚至丢失，但任务结果不能因此消失。

因此，通知只是让系统更快醒来。真正决定“任务完成了没有、产物在哪里”的，始终是任务本身；恢复检查还能补上没有被及时看见的变化。

任务状态还不是 Agent 的新判断

“第七张图片已经完成”只是机器状态。Agent 需要看到的是：这一批素材完成了多少、得到哪些可用产物、原来的创作目标是否仍然需要它们。

Monitor 不替 Agent 做决定。它把同一批任务的最新变化整理成一次新的感知，送进 Inbox，唤醒下一次 Run。模型醒来以后还要重新读取项目：如果开场已经被剪短，就针对现在的时间线作判断，而不是把几十秒前的安排重新覆盖回来。

Clock 解决的是另一类等待：不是“Task 完成时通知我”，而是“未来某个时间让我再检查一次”。到点以后，Clock 把一条 reminder 送入 Inbox，走相同的恢复入口。它是持久唤醒，不是让进程 sleep。

这和 Coding Agent 处理长命令有相似之处。Codex 一类工具通常返回一个后台执行会话，Agent 稍后再 wait 或读取输出；Claude Code 的后台 Bash 会立即返回 task ID，把输出写入文件，并在完成后产生任务通知，它的 Monitor 还能持续把监控事件送回当前 Session。

它们的共同结构都是：先取得一个可以追踪的身份，结果稍后再进入上下文。

但视频任务不能只照搬后台进程模型。一个生成任务可能跨越 Task Worker、第三方模型供应商和 Artifact 存储；浏览器和 Agent 进程都可能在它完成前消失。StarCut 因此把 Task 作为持续存在的业务事实，把通知降级为加速发现的提示，再用 Monitor 和恢复检查接住丢消息与重启。

七、回头看，完整架构是怎样长出来的

现在再看 StarCut 的 Video Agent Loop，它不是先画出一张复杂架构图，再给每个方框找用途。它是从一个最小 ToolLoop 开始，被视频创作的真实约束一层层推出来的：

  1. 模型需要观察和行动，于是有了 ToolLoop。
  2. 视频领域的方法不能全部塞进 Prompt，于是 Tool 与 Skill 分开。
  3. Tool 在不同位置执行，于是有了 Human、Server Runner、Client Runner 和 Task Worker。
  4. Tool Call 必须先于副作用留下事实，于是有了持久消息和统一的 toolCallId 结果路径。
  5. 浏览器是实际编辑现场，外部 Agent 又需要进入，于是 MCP、CLI 和内置 Agent 必须向统一 API 收敛。
  6. 现场能力不能被多个窗口重复执行，于是有了长连接和 Client Lease。
  7. 视频任务比一次 Run 活得久，于是有了 Inbox、Monitor、Clock 和可恢复 Session。

内循环解决“拿到当前结果以后，下一步做什么”；外循环解决“当前 Run 已经结束，新的世界变化怎样让 Agent 再次开始”。Agent 操纵画布，则是两层循环最终闭合的地方：模型产生语义操作，统一 API 改变项目，新的画布现场又成为下一步判断的依据。

DeepSeek Harness 能不能接住这套系统，也应该按这条边界判断。模型适配、Session Log、Inbox、Tool Pipeline 和基础 Agent Loop 越通用，越值得交给 Harness；视频项目语义、领域 Tool、Task 与 Artifact、Monitor 的任务认知和 Editor 执行权，仍然应该由 StarCut 定义。

判断标准很简单：接入以后能删除一套通用循环，就是架构收敛；如果只是把现有系统包成一组插件，概念一个没少，那只是在外面又加了一层。
